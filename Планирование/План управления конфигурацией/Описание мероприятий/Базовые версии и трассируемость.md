## Базовые версии и трассируемость

### Правила введения новых версий

Различные базовые версии проекта вводятся следующим образом:

1. *Базовая версия репозитория*. Базовая версия репозитория представлена последним commit'ом в ветке master, то есть меняется при каждом новом изменении, занесённом в master, и идентифицируется хэшом commit'а.
1. *Базовые версии единиц конфигурации*. Базовые версии ЕК совпадают с той базовой версией репозитория, при которой были внесены изменения и эти ЕК.
1. *Релизная версия проекта*. Так как используется итеративная модель жизненного цикла, то новая релизная версия проекта будет вводиться при завершении итерации. Некоторому коммиту присваивается специальный тег, символизирующий очередную базовую версию приложения. Для этого предназначена команда `git tag`. Номер новой версии формируется в соответствии со спецификацией Semantic Versioning 2.0.0 [1]. Согласно этому стандарту номер формируется в соответствии с шаблоном **MAJOR.MINOR.PATCH**. **MAJOR** - целое число номера версии, увеличивающееся при релизе обновлений, ***несовместимых*** с предыдущими. **MINOR** - целочисленный идентификатор номера версии, увеличивающийся при внесении ***обратносовместимых*** изменений функционала. **PATCH** - идентификатор версии, увеличивающийся только при внесении обратносовместимых изменений функционала для ***исправления*** некорректного поведения. 
1. *Базовая версия для review*. Базовая версия для review представленна последим в истории определённого merge request commit'ом, после которого стоит removed Work In Progress status, и идентифицируется хэшом этого commit'а.
1. *Базовая версия для merge в master*. Базовая версия для merge в master представлена commit'ом, соответствующим тем же требованиям, что и в случае с базовой версией для review, но после rebase.


### Контроль библиотек ПО

Контроль библиотек ПО будет осуществляться при помощи пакетных менеджеров. В JavaScript используется npm, а в Golang gomod.
В специальных конфигурационных файлах выписываются все библиотеки, от которых зависит данное ПО и версии этих библиотек.  При сборке проекта пакетный менеджер устанавливает библиотеки нужных версий.
Библиотеки js скачиваются из стандартного хранилища npm: https://registry.npmjs.org/ (этот источник используется по умолчанию; менять его в настройках npm в рамках данного проекта запрещено).
npm использует конфигурационный файл с именем `package.json`.
Для скачивания всех зависимостей, указанных в `package.json`, необходимо в дирректории с этим файлом использовать команду **npm install**. При этом пакеты будут загружены из источника, указанного в настройках npm (то есть из https://registry.npmjs.org/, если не был изменён источник по умолчанию).
Пример `package.json` файла
```json
{
    "dependencies": {
      "vue": "2.5.2"
    }
}
```

gomod использует конфигурационный файл с именем `go.mod`.
Для скачивания всех зависимостей, указанных в `go.mod`, необходимо в дирректории с этим файлом использовать команду **go mod download**. При этом не существует общего хранилища пакетов. Они располагаются в своих репозиториях git и скачиваются командой **go mod download** прямо оттуда.
Пример `go.mod` файла
```go
module module_name

go 1.12

require (
	github.com/gorilla/mux v1.7.3
	github.com/stretchr/testify v1.4.0
)
```

Исходный код используемых сторонних библиотек для повышения надежности дублируется в собственное хранилище. В это хранилище добавляются все необходимые для проекта зависимости. Это позволяет свести к нулю зависимость от внешних ресурсов, так как уничтожает риски потери частей исходного кода приложения.

### Трассируемость

Базовые версии отдельных единиц конфигурации не устанавливаются, вместо этого используется базовая версия репозитория как такового. Так как есть 3 репозитория: документация, серверная часть и клиентская часть &mdash; то все трассировочные ссылки будут корректны в рамках некоторой версии всего репозитория в целом. Использование нумерации версий по Semantic Versioning 2.0.0 гарантирует синхронизацию версий всех репозиториев.

В данном проекте сохраняется информация о трассировке между:

* Требованиями к системе и требованиями к ПО.
* Требованиями к ПО и описанием проекта (ЕК: артефакты проектирования).
* Описанием проекта и исходным кодом (ЕК: функция или класс).
* Требованиями к ПО и исходным кодом (в некоторых случаях).
* Требованиями к ПО и тестовыми процедурами (ЕК: функция или класс).
* Исходным кодом и тестовыми процедурами.
* Issue и merge request.

1. Трассировка между **требованиями к системе**, **требованиями к ПО** и **описанием проекта** устанавливается при помощи трассировочного инструмента `trace.py`, расположенного в репозитории *DM4-LogicalCalculus.Docs* в папке *trace*. Документация к данному инструменту расположена в той же папке в файле *README.md*, а также в подразделе *Трассировочная база данных* данного документа.

1. Трассировка **требований к ПО** и **описания проекта** на **исходный код** не производится.

1. Для достижения трассируемости **исходного кода** на **артефакты проектирования** и **конкретные требования** в комментарии над участком исходного кода устанавливается ссылка на требуемый источник. Способ записи данной ссылки указан в *Стандарте на кодирование*.

1. Для достижения трассируемости **требований** на **тестовые процедуры** и **тестовых процедур** на **требования** в файл *Данные о трассировке* в таблицу записывается информация о соответствии каждого конкретного требования определённой тестовой процедуре. Также записывается версия требования с точностью до конкретного коммита. Идентификация требований описана в *Стандарте на разработку требований*. Идентификация тестовых процедур описана в *Плане верификации*.

1. Трассировка между **исходным кодом** и **тестовыми процедурами**, исполняющимися автоматически, устанавливается исходя из записи тестовых процедур.

1. Трассировка между **исходным кодом** и **тестовыми процедурами**, выполняющимися вручную, не требуется.

1. Трассировка между **Issue** и **Merge request** устанавливается автоматически самим Gitlab'ом. В описании issue указываются ссылки на все merge request, а у merge request есть ссылка на связанную с ним issue.
