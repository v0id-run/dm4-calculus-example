# Методы верификации

## Ревью

В данном разделе описан процесс ревью. *Объектом ревью* является один или несколько файлов (иногда только их определенные части), находящихся в репозитории. В контексте мероприятия ревью выделяются следующие роли:

* *Commiter* - участник команды, который вносит изменения в объекты ревью.
* *Approver* - член команды, имеющий знания в области, относящейся к объекту ревью, и оценивающий корректность изменений Commiter'а.
* *Author* - участник команды, создавший issue для изменения или создания объектов ревью.


### Входные данные

* объекты ревью;
* merge request, содержащий коммит с изменениями объектов ревью. 

### Критерии начала мероприятия

1. Были внесены изменения в объекты ревью.
2. Merge request находится в статусе "Resolved".

### Процедура выполнения мероприятия

Commiter на странице с merge request убирает префикс WIP:  из заголовка merge request'a, показывая тем самым, что изменения, которые он внёс, готовы к ревью. Это можно сделать путём нажатия на кнопку Resolve WIP status.

Author регулярно просматривает состояние merge request'ов. Когда появляется merge request, готовый к ревью, Author назначает Approver'а для данного merge request'а. Commiter не может получить роль Approver'а.

Approver фиксирует выявленные ошибки в виде комментариев к merge request'у. Если ошибки были найдены, то Approver добавляет в описание merge request префикс WIP:  путём непосредственного редактирования описания merge request'а.

### Регистрация результатов

Commiter вносит дополнительные изменения, устраняющие выявленные ошибки, и добавляет их в свой merge request. Если Approver считает, что issue полностью решена, а изменения не содержат ошибок, они нажимают кнопку Approve на merge request. Это значит, что изменения можно добавлять в основную версию проекта.

### Критерии окончания мероприятия

* Если Approver'ом оставлен хотя бы один комментарий и по каждому комментарию Commiter внес изменения в объекты ревью;
* Merge request находится в статусе 'Approved'.

### Выходные данные

Merge request в статусе 'Approved'. 

## Инспекция 

В данном разделе дано описание типового процесса формальной инспекции. *Объектом инспекции* будет являться один или несколько файлов, находящихся в репозитории. В контексте мероприятия формальной инспекции выделяются следующие роли:

* *Initializer* - инициатор инспекции.
* *Inspector* - инспектор, член команды, имеющий знания в области, относящейся к объекту инспекции, но в то же время, не участвовавший в создании данного объекта.
* *Author* - участник команды, вносивший изменения в объект инспекции.

### Входные данные

* объекты инспекции;
* план верификации ПО;
* issue для инспекции.

### Критерии начала мероприятия

Установлены базовые версии входных данных.

### Процедура выполнения мероприятия

#### Инициация 

Инициатор инспекции создает issue с пометкой `type::Inspection`, при этом использует шаблон *Inspection*:

@import "../../.gitlab/issue_templates/Inspection.md"

Затем инициатором назначаются инспекторы: один или несколько человек, а также блокируется возможность внесения изменений в объекты инспекции:

* либо путём нажатия кнопки *Lock* в интерфейсе gitlab у конкретных файлов, содержащих объект инспекции;
* либо путём указания о запрете слияния ветки merge request'ов, которые содержат изменения в объекте инспекции.

#### Экспертиза и обсуждение

Инспекторы проверяют те характеристики объекта инспекции, которые указаны в описании issue. Если проверка окончена, то инспектор помечает соответствующий пункт в описании issue галочкой. Если обнаружено несоответствие, то инспектор оформляет замечание. Каждое найденное замечание фиксируется в комментариях к issue в следующем формате:

**Расположение.** `[link](<file_path>#L<x1>-<x2>)`

**Замечание.** (обязательно)

**Решение.** (если возможно)

`<x1>` и `<x2>` - это числа, обозначающие диапазон строк, к которым относится замечание.

Рекомендуется в одном комментарии оставлять комментарии к одному файлу, особенно, если это касается исправления опечаток, орфографических или пунктуационных ошибок. Отдельный комментарий на некоторое замечание можно заводить, если инспектор хочет обсудить решение данного замечания отдельно.

#### Регистрация результатов

По каждому комментарию, оставленному инспекторами, открывается обсуждение между инициатором инспекции, инспектором и авторами. По итогам обсуждения замечание может быть отклонено, и тогда к комментарию присоединяется эмодзи `thumbs down sign`. Если же замечание принято в работу, то к комментарию присоединяется эмодзи `thumbs up sign` и последним ответом к комментарию указывается номер issue в формате `#<number>`, в котором решается данное замечание.

### Критерии окончания мероприятия

Выполняются следующие условия:

* все инспекторы оставили не менее одного комментария;
* по каждому комментарию принято решение о необходимости исправления - у каждого комментария есть эмодзи;
* внесены все исправления по замечаниям - около каждого номера issue появилась пометка вида `#<number> (closed)`.

В момент выполнения этих критериев, issue переводится в состояние *Closed*.

### Выходные данные

Issue с тегом `type::Inspection`.

### Исправление несоответствий

После того как все issue по замечаниям выполнены, ведущий переводит issue формальной инспеции в статус Closed.

## Методы тестирования

Система будет тестироваться следующими методами:

* **функциональные**:

    * *метод черного ящика*: система проверяется на наличие ошибок в работе функционала при условии, что тестировщик не имеет информацию о внутреннем устройстве системы и логике работы кода;

    * *тестирование безопасности*: система проверяется на обеспечение конфиденциальности (каждый вид пользователей имеет доступ только к определенной информации), доступность (ресурсы доступны только авторизированным пользователям) и целостность (изменение ресурсов доступно только определенным группам пользователей);

* **нефункциональные**:

    * *нагрузочное тестирование*: система проверяется на работоспособность путем симулирования одновременной работы множества пользователей;

    * *тестирование совместимости*: система проверяется на совместимость с различными операционными системами и браузерами;

    * *usability-тестирование*: система проверяется на обучаемость, запоминаемость, удобство пользования.

### Методы выбора тестовых примеров

Тестовые примеры будут опроределяться исходя из функциональных требований. При тестировании функциональности программы применяется подход "черного ящика", то есть для каждого требования к системе формируются тест-требования, которые, как правило, детализируют функциональные требования так, что на одно функциональное требование может приходиться несколько тест-требований. Сами тест-требования определяют, что должно быть протестировано, но не определяют, как. Конкретные значения задаются в тестовых примерах. Таким образом, одному тест-требованию может соответствовать сразу несколько тестовых примеров.

### Тестовые процедуры

Тестовые процедуры будут оформлены в виде таблиц, где первый столбец соответствует одному из действий, выполняемых для проверки определенного тестового случая, а второй - результату проверки данного шага.
