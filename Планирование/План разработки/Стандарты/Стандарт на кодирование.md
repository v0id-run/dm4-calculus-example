## Cтандарт на кодирование

1. Используемые языки программирования и их подмножества:
    * Язык программирования Go (для кодирования backend). Спецификация используемой версии языка расположена в файле *Планирование/План разработки/Приложения/GO-1.13.4.pdf*.
    * Язык программирования JavaScript (для кодирования frontend). Спецификация используемой версии языка расположена в файле *Планирование/План разработки/Приложения/ECMA-262.pdf*.
    * Фреймворк Vue.js языка программирования JavaScript (для кодирования frontend). Ссылка на документацию к фреймворку расположена в файле *Планирование/План разработки/Ссылки.md* [1].

2. Стандарты на форму представления исходного кода:
    * Отступы представлены табуляциями.
    * Выравнивания представлены пробелами.
    * Фигурные скобки, содержащие блоки кода, должны открываться на строке, предшествующей блоку (но не на новой относительно предшествующего кода) и закрываться на следующей строке после блока кода (на этой строке кроме закрывающейся фигурной скобки никаких символов быть не должно). Допускается использование такого же стиля записи для обычных скобок, если в противном случае строка кода занимает более 100 символов.
    * Внутри функции между строками кода должно быть не более одной пустой строки.
    * Между блоками импорта модулей, объявления констант, описаниями структур, и функциями пропускается по две пустых строки (если тот или иной блок начинается с комментария, то строки пропускаются между концом предыдущего блока и началом комментария).
    * В первых строках модуля в виде комментариев указвается: название и версия модуля; имя автора и дата создания версии модуля; краткое описание модуля; входы и выходы модуля (в случае, если он представляет из себя самостоятельно функционирующую единицу); изменения глобального окружения (создание, редактирование или удаление файлов, изменение глобальных переменных ОС и т.д.), которые в ходе своего функционирования может производить модуль (если таковые имеются). 
    Примечания:
        * В случае JavaScript под модулем подразумевается один файл или совокупность взаимосвязанных файлов, полностью обслуживающих одну или несколько web-страниц. Информация о модуле указывается только в главном файле модуля, т.е. в файле, который импортирует все остальные и с помощью них реализует необходимый программный интерфейс. 
        * В случае Go под модулем подразумевается пакет (**package**). Описание модуля также необходимо указывать только в основном файле пакета.
    * Над описанием структур и над функциями в виде комментариев кратко описывается их назначение. Также обязательно комментируется назначение полей структур и опционально строки в функциях.
    * Для тех модулей, функций и структур, которые представляют собой реализацию артефакта проектирования и/или конкретного требования (не являются вспомогательными), в целях обеспечения трассируемости, в комментарии указывается ссылка на соответствующий артефакт проектирования и/или требование. Оформление трассировочных комментариев в коде:
        * Трассировочный комментарий располагается над всеми остальными, относящимися к данному модулю, функции или структуре.
        * Трассировочный комментарий имеет следующий вид:  
            "трассировочный комментарий" ::=   
                // Trace designing artifact: "ссылка на артефакт проектирования" |  
                // Trace requirement: "ссылка на требование"  
            Ссылки на требования и на артефакты проектирования представляют из себя ссылки на соответствующие файлы с учётом их версии с точностью до конкретного коммита в репозитории **gitlab**. Пример ссылки:
            `87f846191f0130f98a2484a9aa6e790338484ef8/images/event_1.png`
        * Если элемент кода представляют собой реализацию и артефакта проектирования, и конкретного требования, то пишется два трассировочных комментария. Первым пишется коммментарий, относящийся к требованию. В случае, если элемент кода является реализацией сразу для нескольких требований, то ссылки на них указываются последовательно (и, если необходимо, после них указывается ссылка на артефакт проектирования).

3. Правила наименования компонентов:
    * Именование переменных, констант и функций в Go происходит в одном из стилей: **PascalCase** (если компонент должен быть экспортируемым) или **camelCase** (если компонент должен быть не экспортируемым).
    * Имена пакетов Go должны содержать только строчные буквы и быть представлеными одним словом. Имена файлов должны соответствовать стилю **snake_case** и иметь расширение ".go".
    * Для именования констант, объектов, функций и переменных в JavaScript использовать **camelCase**. Для конструкторов классов - **PascalCase**. Использовать подчеркивание "_" в качестве префикса для именования внутренних методов и переменных объекта.
    * При именовании файлов кода на JavaScript допускается использование строчных букв и цифр, а также символов "." и "-" в качестве разделителей слов в составе имени. Файлы должны иметь расширение ".js".

4. Условия и ограничения, накладываемые на принятые соглашения о приёмах
кодирования:
    * Пакеты Go, из которых состоит backend должны быть организованы в единую иерархическую структуру с единственным пакетом main и функцией main, запускающей все компоненты системы. Структура проекта соответствует стандарту, описанному в репозитории ***golang-standards/project-layout***.
    * Код на JavaScript представлен отдельными модулями, обеспечивающими нужды определённых html страниц (взаимосвязь не обязательна).
    * Логические и численные выражения, длина строк с которыми составляет более 100 символов, должны быть либо сокращены путём введения новых переменных, либо вынесены в отдельные функции.

5. Ограничения на применение инструментов кодирования:
    * Не использовать в текстовых редакторах или IDE замещение табуляции пробелами и наоборот.
    * Используемый редактор должен поддерживать кодировку UTF-8.
    * Используемый редактор должен корректно воспринимать переносы строк и в стандарте Windows, и в стандарте Linux.

6. Вспомогательные инструменты для форматировния исходного кода:
    * Единство формата записи исходного кода контролируется официальной утилитой gofmt.
    * Единство стиля исходного контролируется официальной утилитой golint.
